Ambos Security · remote support access

Disposable Support Sessions

The customer calls. An engineer clicks Connect. A container dials into that customer's network and hands over a browser that is already inside it. When the call ends, the browser, the tunnel and the credentials are destroyed.

Lab · built and verified Session containers · production code already Customer pilot · not started

01 — THE IDEAAccess as an event, not a state

Two claims, and both are structural — consequences of how it is built, not promises about how it is used.

ClaimEnforced by
Access is off by defaultThere is no container, no browser and no tunnel until somebody clicks Connect.
One session reaches one customerAllowedIPs — the session's routing table contains that customer's subnet and nothing else. Not a policy: a route that does not exist.

This is the opposite of the remote-desktop model. Nothing is installed on a customer PC, nobody has to be present, and no one's desktop is taken over. What you get is a network position — the ability to open https://camera-01 — which is far less than remote control and far easier for a security team to approve.

02 — LOCALLYWhat runs on the laptop today

Everything is prefixed sb-. Only one part of this picture is a simulation; the session containers are production code, unchanged.

What the resolver is for

Without it, an engineer types IP addresses. The resolver is dnsmasq running inside the session, serving that one customer's device names, with the browser's /etc/resolv.conf mounted to point at 127.0.0.1:

exec dnsmasq --listen-address=127.0.0.1 --no-resolv --no-hosts \
  --addn-hosts=/etc/devices.hosts   # rendered from session-manager/devices/<customer>.json
  --server=127.0.0.11               # anything else → Docker's resolver

So the engineer types camera-01.acme.internal, not 172.31.90.10. Names the customer doesn't own still resolve normally, the list exists only inside that session and only for that customer, and it dies with it. Nobody edits a hosts file on any laptop, ever.

If a customer runs their own DNS server on that LAN, one extra flag — --server=/acme.internal/192.168.131.1 — forwards their zone to them instead, so names never go stale. Their resolver must be inside AllowedIPs; thanks to the NAT at the site gateway, your queries arrive looking like they came from a machine on their own LAN.

03 — THE SEQUENCEWhat one click actually does

From pressing Connect to looking at a camera. Seven steps, no magic in any of them.

  1. The page calls the API.

    The Connect button is nine lines of JavaScript. It posts, then reloads the page.

    await fetch('/api/sessions/customer2', {method: 'POST'});
  2. Traefik stops the request and asks authentik.

    Forward auth — see §05. Only a 200 OK lets it continue to the session manager.

  3. The session manager checks the customer exists, then runs a script.

    The same script a human would run at the terminal. One code path, so it cannot drift.

    if cid not in {c["id"] for c in customers()}:
    raise HTTPException(404, "unknown customer")
r = run("session-up.sh", cid)
audit("start", cid, r.returncode == 0)
  4. The script renders this customer's config and calls Compose.

    Note HOST_DIR: bind-mount paths are resolved by the Docker daemon on the host, so the session manager must pass the host's path, never its own /project.

    SESSION_ID="$SESSION_ID" WG_CONF="${HOST_DIR}/${CONF}" \
docker compose -f session/docker-compose.session.yml \
  -p "sb-session-${SESSION_ID}" up -d --build
  5. The vpn container starts and opens the tunnel.

    Its entrypoint runs wg-quick up wg0, which reads the mounted config, creates the interface, and installs one route per AllowedIPs entry.

  6. The browser starts inside that container's network.

    network_mode: "service:vpn". Docker gives it no IP and no interfaces. It can reach exactly what the tunnel reaches, and nothing else.

  7. Traefik notices the new container and routes to it.

    It is subscribed to Docker's event stream, reads the container's labels, and creates a router for customer2.sb.test within a second. The page reloads and the row now shows Stop and Open.

Worth noticing

The session manager never touches the tunnel. It only asks Docker for containers — the tunnel is opened by the container itself, at step 5, using the config that was mounted into it. The session manager's entire job is create and destroy.

04 — THE FILESThe four that carry the design

Everything above is these. Nothing else in the repo is load-bearing.

session/docker-compose.session.yml — the whole idea, in forty lines

services:
  vpn:
    build: ../session/vpn
    cap_add: [NET_ADMIN]            # may create wg0 and set routes
    volumes:
      - ${WG_CONF}:/etc/wireguard/wg0.conf:ro
    labels:                         # NOTE: labels live HERE, not on the browser
      - traefik.http.routers.${SESSION_ID}.rule=Host(`${SESSION_ID}.${LAB_DOMAIN}`)
      - traefik.http.services.${SESSION_ID}.loadbalancer.server.port=3000

  browser:
    image: lscr.io/linuxserver/firefox:latest
    network_mode: "service:vpn"     # ← the isolation guarantee, one line
    depends_on: [vpn, resolver]

The Traefik labels sit on the vpn container and point at port 3000 — Firefox's port. A container with no IP cannot be routed to, so the namespace owner carries the routing and points at the port its tenant listens on. Put the labels on the browser instead and Traefik silently creates no router at all.

session/vpn/entrypoint.sh — what opens the tunnel

#!/bin/sh
set -eu                          # die on any failure, rather than run without a tunnel

wg-quick up wg0                  # reads /etc/wireguard/wg0.conf, adds the routes
wg show wg0   | sed 's/^/[vpn]   /'
ip route      | sed 's/^/[vpn]   route: /'   # the audit line: one customer, one route

trap 'wg-quick down wg0 || true; exit 0' TERM INT
while :; do sleep 3600 & wait $!; done   # ← never finish

Two things here are deliberate. A container lives exactly as long as its main process, so if this script ended the namespace would be destroyed with the browser inside it — hence the endless loop. And sleep & wait rather than a plain sleep, because a shell will not run a trap while a foreground command is still running: wait is interruptible, so docker stop is honoured immediately.

session-manager/app.py — start, stop, and the record

def run(script, cid):
    """Sessions are started by the same scripts a human would run."""
    return subprocess.run([os.path.join(PROJECT, "scripts", script), cid], ...)

def live():                       # no database anywhere — ask Docker
    out = subprocess.run(["docker", "ps", "--filter", "name=-vpn", ...]).stdout
    # sb-customer2-vpn → customer2

def audit(action, cid, ok):       # append-only, outside the session
    fh.write(f'{now}\t{action}\t{cid}\t{"ok" if ok else "FAILED"}\n')

The session manager keeps no state. It asks Docker what is running, so it can never disagree with reality, can be restarted mid-session, and has nothing to corrupt or back up. Its power comes entirely from two mounts — the Docker socket and the project directory — which is also why it is the most security-critical container you will run.

session/conf/customer2.conf — the tunnel's identity, lab version

[Interface]
Address    = 10.13.13.3          # my address inside the tunnel
PrivateKey = <this session's key>

[Peer]
PublicKey  = <the customer end's key>
Endpoint   = sb-wg-server:51820  # ← a container name. This is the lab-ism.
AllowedIPs = 172.31.90.0/24      # route out AND filter in — one customer only

AllowedIPs does two jobs: outbound it becomes a route (send this subnet down the tunnel), inbound it is a filter (accept nothing else from this peer). One line, and it is the whole "one session, one customer" guarantee. Every customer gets its own key pair — sharing one silently breaks the second session, because a WireGuard server tracks one endpoint per public key and the newer handshake steals the older tunnel.

05 — THE DOORauthentik, and why it is not inside the session manager

The console is a page whose buttons open tunnels into customer networks. It needs a lock — but not one bolted onto the most dangerous container in the system.

The session manager holds a read-write Docker socket, which is equivalent to root on the host. Adding accounts, password hashing, sessions and MFA to that would mean the most privileged thing you run is also the one with the most hand-written code in it. So the door goes in front instead.

two labels, and the session manager never knows

# on the session manager's router:
- traefik.http.routers.session-manager.middlewares=ak-auth@docker

# on authentik, defining that middleware:
- traefik.http.middlewares.ak-auth.forwardauth.address=http://ak-server:9000/outpost.goauthentik.io/auth/traefik
- traefik.http.middlewares.ak-auth.forwardauth.authResponseHeaders=X-authentik-username,X-authentik-groups

Where to use it, and where not

SurfaceGuarded?Why
The consoleYesIts buttons open tunnels. This is the door that matters most.
Session URLsNot yetSee the gap below — this must be closed before a real credential exists.
Inside the sessionNoThe customer's own devices have their own logins. We are a network position, not an identity.
Known gap — not built

A live session's browser answers without a login: curl -H 'Host: customer2.sb.test:8088' … returns 200. authentik's forward_single mode covers exactly one hostname. forward_domain would cover the console and every session with one provider; it was tried twice — under .localhost the cookie is rejected outright (a single-label TLD is a public suffix), and under sb.test the cookie is valid but the outpost still answers 404 for every host. That second failure is unresolved — do not assume a real domain fixes it.

The better answer, and the one on the roadmap: the session manager creates a provider per session through authentik's API. That also buys what forward_domain cannot — which engineer may open which customer, rather than only who may log in.

06 — REAL LIFEWhere the tunnel actually goes

The session half needs no changes at all. What changes is where the tunnel terminates — and that single change inverts who dials whom.

The entire ask on the customer becomes one sentence: this device needs to send outbound UDP to one address. No inbound firewall rule, no port forward, no public IP, no DMZ — the same category of traffic as their browser and their email client.

Why outbound-only is the whole sales pitch

The obvious alternative is to ask the customer to open a port and forward it to the box. That request is refused by every competent security team, and they are right to refuse it — a forwarded port is reachable by the entire internet, not just by you.

EndDirectionTheir firewall must allowExposed to the internet
The site gatewayoutbound onlyoutbound UDP to one address:portnothing
Our sessionoutbound only— (our side)nothing
The hubaccepts inbound— (ours, and it is meant to)one UDP port
A detail worth having ready when they push back

Even the hub is quiet. WireGuard never replies to a packet that is not signed by a known key — no handshake, no error, no reset. To a port scanner the hub looks like a closed port on a dead host. There is no banner to fingerprint and no login to brute-force, because there is no login.

So the honest summary for a customer: you install nothing, you change nothing on your firewall, and nothing on your network becomes reachable from outside. The one requirement is that a device on your LAN may send outbound UDP — which their browser already does.

How the tunnel gets created, step by step

  1. Generate a key pair for the site.

    One per site, never shared. The public half goes into the hub's config; the private half goes into the gateway's, and nowhere else.

    wg genkey | tee site-acme.key | wg pubkey > site-acme.pub
  2. Add the site as a peer on the hub, with a route to their LAN.

    AllowedIPs on the hub is what tells it "traffic for that subnet goes to this peer."

  3. Deliver the config to the site over a channel that is not email.

    That file is the key to their network. Later this comes from Infisical and never lands on disk at all.

  4. The gateway dials out and keeps the hole open.

    PersistentKeepalive = 25 sends a tiny packet every 25 seconds so the customer's NAT does not forget the mapping. This is what lets us start a session hours later.

  5. On Connect, the session becomes a peer too — and only then.

    Its AllowedIPs is that one customer's LAN. The hub forwards between the two peers; per-peer rules stop it forwarding anywhere else.

the session's wg0.conf — real, rendered per session

[Interface]
Address    = 10.8.0.60/32

[Peer]

the site gateway's wg0.conf — lives on the robot or the box

[Interface]

[Peer]

the hub's wg0.conf — one block per end

[Peer]                                # a session, added when one exists
PublicKey  = <session public key>
AllowedIPs = 10.8.0.60/32

Two settings on the gateway do all the work

SettingWhat it buys
ip_forward = 1Off by default on Linux — a normal machine accepts traffic for itself and drops the rest. On, it becomes a router: the tunnel gets you to the gateway, this gets you past it.
MASQUERADE
(ENABLE_NAT=1)		The reason the customer changes nothing. Traffic off the tunnel is rewritten to appear to come from the gateway — an address their devices already know and already route back to. Without it you would need a static route added to their router, at every customer, with a change ticket each time.
Say this before your senior asks

There is one standing tunnel: gateway → hub, held open by keepalive. But it is a pipe with nobody at the other end. No session exists, no browser exists, and the hub's rules give the site peer nobody to talk to until a session appears.

The path exists; the access does not. If a customer wants even the pipe closed, the box can hold only a control channel and bring the tunnel up when told — same outbound-only shape, and our side is identical either way. Something has to be reachable in order to be woken up.

07 — THE FAR ENDGetting a foothold at the customer

A tunnel has two ends. Something must exist on their network — there is no way around it. What varies is how much you are asking of them.

FormWhat you are askingVerdict
Their firewall already speaks WireGuard, IPsec or OpenVPNa config entry from their ITCommon in businesses. Cheapest, but on their schedule.
A robot is already on sitenothingAlready installed, already powered, already approved. This is the answer wherever it applies.
You ship a small box"plug this into a network port"Hardware, not software. No install, no admin rights, no PC touched.
Nothing at all—Impossible. Don't promise it — fall back to §07 below.

The robot is already a site gateway

fleet-management ships two services to every robot, and both are defined but dormant — they sit behind a Compose profile, so docker compose up ignores them until you ask for them by name.

  wireguard-client:
    profiles: ["vpn"]          # ← shipped, not started
    volumes: [ {source: ${WG_CONFIG_HOST_FILE}, target: /run/wireguard/wg0.conf} ]

  lan-over-vpn:
    profiles: ["vpn"]
    privileged: true             # needed to set host sysctls (ip_forward)
    environment:
      LAN_IFACE:  "${LAN_IFACE:-br0}"
      LAN_CIDR:   "${LAN_CIDR:-192.168.131.0/24}"
      ENABLE_NAT: "${ENABLE_NAT:-1}"

Turning a robot into a site gateway is therefore not an install. It is naming a profile:

docker compose --env-file "$robot/robot-services.env" \
  -f services/docker-compose.yml -f deploy/platforms/<platform>/docker-compose.yml \
  --profile vpn up -d --build wireguard-client lan-over-vpn
And the delta is smaller still

Robots already run wireguard-client — that is how fleet management reaches them. The tunnel from robot to hub already exists and is already up. The only missing half is the forwarding: ip_forward + NAT, so traffic arriving on wg0 can continue onto the customer's LAN instead of stopping at the robot.

How you reach the robot to switch it on

RouteStateNotes
Over the tunnel that already existsworks todayThe robot is on the hub's subnet. SSH in, run the command. Fine for a pilot; a human with SSH access to customer hardware is not the permanent answer.
Over NATS, via admin-bridgepartly builtThe robot already runs a NATS listener accepting named, authorised actions (today: recover-stack, with signed authorisation and replay protection). A second action — bring up support access — is the clean answer: the robot decides, logs it, and can refuse.
Set at commissioningworks todayConfigure robot-services.env before the robot ships. Nobody has to reach it later.

One flag: privileged: true on lan-over-vpn is a real privilege — it exists because Docker blocks writes to host network sysctls otherwise. The service writes nothing to the robot's filesystem and removes its iptables rules when stopped, which is the right mitigation, but the word will come up in a security review. Know why it is there first.

If the customer refuses everything

Then you drive there, and that always works — no tunnel, no hub, no keys. It is the baseline this whole system is measured against, so measure it:

09 — NOT BUILT YETBefore a paying customer

In order. Each one, missing, makes the system worse than the ad-hoc VPN it replaces.

#WhatWhy it is that high
1Auth on session URLsToday a live session's browser answers anyone who can reach the host — an unauthenticated door into a customer network, open as long as the session is. See §05.
2An idle reaperSESSION_IDLE_MINUTES exists in .env.example and nothing reads it. A forgotten session is a standing tunnel into a customer's network — the exact thing this design exists to abolish.
3Credentials from InfisicalThe lab writes the key to disk. Production fetches it at start, passes it in memory, and it dies with the container.
4Isolation at the hubA single flat hub puts every peer in one subnet and will forward between them. Restore the guarantee with per-peer firewall rules, or one WireGuard interface per customer — the latter makes it structural again.
5A real hostAlways-on, and roughly 8 GB for three concurrent sessions. A support tool that is asleep when a customer calls is not a support tool.
6Names and certificatesconsole.sb.test becomes a real domain. Session hostnames can stay internal — only staff reach them.
7The audit log, somewhere realA file inside the session manager container is evidence only until the container is recreated.
Standing rule

Until item 1 is closed, the lab must not hold a real customer credential.

Open questions — verify, do not assume

  • Who administers the hub, may we add peers to it, and does it forward between peers?
  • Does the site's firewall permit outbound UDP 51820? Test this before demo day, not on it.
  • Overlapping LANs: two customers both on 192.168.1.0/24 collide at the hub. Fine for one site; decide the fix — a unique carrier subnet per site, 1:1 NATted at the gateway — before the second customer, not after.
  • Does lan-over-vpn handle a session reaching in, as opposed to the robot reaching out? The NAT direction should make it work. Untested.
