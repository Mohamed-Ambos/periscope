Session Manager Lab

Thirteen containers on one laptop. Six are ours, two pretend to be a customer, and three appear only while an engineer is working. Here is what each one is, and what it stands for in real life.

This is not a proposal any more. It runs, and every claim below was checked against the running system rather than reasoned about.

Repository: github.com/Mohamed-Ambos/periscope — nothing from the company was touched.

04 · No more hosts files

A JSON file per customer, and a resolver per session

Cameras have static IPs, so the mapping from name to address is just data. Keeping that data in one file per customer — instead of in a hosts file on every laptop — is the whole fix.

// session-manager/devices/customer2.json
{
  "customer": "customer2",
  "domain":   "acme.internal",
  "devices": [
    { "name": "camera-01", "ip": "172.31.90.10", "kind": "camera", "model": "AXIS P1375" },
    { "name": "nvr",       "ip": "172.31.90.20", "kind": "recorder" }
  ]
}

Verified from inside the running browser container:

$ docker exec psc-customer2-browser getent hosts camera-01.acme.internal
172.31.90.10    camera-01.acme.internal

$ docker exec psc-customer2-browser curl -sk -o /dev/null -w '%{http_code}' https://camera-01.acme.internal/
200

$ docker exec psc-customer2-browser getent hosts github.com     # normal DNS still works
140.82.121.3    github.com

05 · Reaching the customer

How we get in — and why they can accept it

Nothing we run can reach a customer network on its own. The tunnel is always opened from inside their network outwards, which is why no firewall rule has to be negotiated.

SituationWhat opens the tunnelEffort per customer
Site already has one of our robotsThe robot — it already routes between its VPN and the local networkConfig only
Customer runs WireGuardTheir endpoint. We hold a peer credentialConfig only
Customer runs OpenVPN or IPsecTheir endpoint; the vpn image carries that client tooOne-off image work
Customer runs a vendor VPNMay need a vendor client, sometimes a licenceCheck before promising
Customer allows nothingA small box we place, dialling out on demandHardware conversation
What a customer is actually agreeing to

Access that does not exist until someone opens it, is limited to one site, is destroyed afterwards, and is written down every time. That is a much easier conversation than a permanent tunnel into their network — and it is the same conversation whichever row of the table they are in.

06 · State of it

What works, and what does not yet

Login on session URLsnot yetNeeds a real domain — see below
Credentials from Infisicalnot yetThe lab writes them to disk
Idle timeout / reapernot yetSessions run until stopped by hand
The gap that matters, and why it is still open

A live session's browser is currently reachable without logging in. authentik's forward_single mode protects exactly one hostname — the console. forward_domain would cover every session too, but it needs a real registrable domain: with a cookie domain of localhost every request returns 404. That was tried, and that is what happened.

Under a real domain the fix is two lines — switch the provider mode, and uncomment the middleware label that is already sitting in session/docker-compose.session.yml. Until then, this lab must not hold a real customer credential.
